# homelab2

A home lab managed as code with **Flux (GitOps)** on **k3s**. Everything in the
cluster — infrastructure and applications — is described declaratively in this
repository and continuously reconciled by Flux. Authentik provides SSO and
RBAC for all services.

## How it works

- **Flux** watches this Git repo. Each directory under `infrastructure/` and
  `apps/` is reconciled into the cluster; drift is corrected automatically and
  only changed objects are applied.
- **Secrets** are encrypted with **SOPS + age** and committed. Flux decrypts
  them in-cluster using the `sops-age` key.
- **Authentik** is the identity provider. Grafana uses OIDC; services without
  native SSO are protected by an Authentik forward-auth Traefik Middleware.

## Repository layout

```
clusters/homelab/      Flux entrypoints (source, infrastructure, apps, secrets)
                       + flux-system/ (generated by `flux bootstrap`)
infrastructure/        Cluster services, reconciled by Flux
  sources/             HelmRepositories
  cert-manager/        cert-manager HelmRelease (installed first)
  certificates/        Let's Encrypt ClusterIssuers + wildcard Certificate
  reflector/           Replicates the wildcard TLS Secret across namespaces
  traefik/             k3s-bundled Traefik tuning (HelmChartConfig)
  databases/           PostgreSQL, Valkey (Bitnami HelmReleases)
  auth/                Authentik + declarative blueprints (providers, RBAC)
  observability/       kube-prometheus-stack (Grafana), Loki, Tempo
  networking/          Shared Traefik Middlewares
secrets/               SOPS-encrypted Kubernetes Secrets
apps/                  First-party applications
```

Reconciliation order is expressed with Flux `dependsOn`:
`flux-system (source)` → `sources` → `secrets` → `cert-manager` →
`infrastructure` → `apps`.

## Bootstrap (one-time)

```sh
# 1. Install Flux and point it at this repo (creates clusters/homelab/flux-system/)
just bootstrap Rapdorian homelab flux

# 2. Give Flux the SOPS decryption key
just age-secret

# 3. Provide a Cloudflare API token so cert-manager can solve DNS-01
just edit secrets/cloudflare-api-token.enc.yaml
```

The only external prerequisite is a Cloudflare API token scoped to
`Zone -> DNS -> Edit` for `jpruitt.dev`; everything else is automated.

Day-to-day:

```sh
just reconcile   # pull + re-reconcile now (otherwise Flux polls on interval)
just status      # sources / kustomizations / helmreleases
just watch       # follow reconciliation
```

## Secrets

Never added to git in plaintext. Files under `secrets/` are SOPS-encrypted with
age; only `data`/`stringData` are encrypted. The age private key lives in
`~/.config/sops/age/keys.txt` and in the cluster as the `sops-age` Secret.

```sh
just edit secrets/postgres.enc.yaml   # edit in place (decrypts/encrypts)
just encrypt secrets/new.enc.yaml     # encrypt a new secret
```

`secrets/cloudflare-api-token.enc.yaml` is the one value you must supply
manually (the Cloudflare API token). All others are generated.

## TLS and DNS

Because `.dev` is on the **HSTS preload list**, browsers require a publicly
trusted certificate on every `*.dev` host, even those resolving to a private IP.
Traffic never leaves the LAN; only *validation* does.

- The wildcard A record `*.local.jpruitt.dev -> 10.0.0.80` is **DNS-only** in
  Cloudflare (Cloudflare cannot proxy to a private origin). Create it manually.
- cert-manager issues a single wildcard Certificate
  (`infrastructure/cert-manager/wildcard-certificate.yaml`) using the
  **Cloudflare DNS-01 solver** — it writes the `_acme-challenge` TXT record via
  the API, so no inbound access is needed.
- **Reflector** copies the resulting `wildcard-local-tls` Secret into `auth`,
  `observability`, and `default` so each Ingress can reference it locally.
  Add a namespace to the annotation list when you deploy an ingress there.

Check progress with `just certs`. To test against Let's Encrypt staging first,
point a Certificate/Ingress at the `letsencrypt-staging` ClusterIssuer.

## Access control (Authentik)

All services authenticate through Authentik. Configuration is declarative via
blueprints in `infrastructure/auth/blueprints-configmap.yaml`.

**Grafana** logs in via OIDC and its role comes from Authentik group membership
(`role_attribute_path` in `infrastructure/observability/kube-prometheus-stack.yaml`):

| Authentik group  | Grafana role |
| ---------------- | ------------ |
| Grafana Admins   | Admin        |
| Grafana Editors  | Editor       |
| Grafana Viewers  | Viewer       |

To grant a user read/write Grafana, add them to `Grafana Viewers` (read) or
`Grafana Editors` (write) in Authentik — no Grafana-side change needed.
`role_attribute_strict` means users in none of the groups get no role/access.

**Services without OIDC** are protected by the `default-authentik-forwardauth`
Traefik Middleware. Each protected host maps to a proxy provider + application
in Authentik (with group bindings). See `apps/example-app/hello-world.yml` and
the blueprint for the pattern.

## Adding a service

1. Add manifests/kustomization under `apps/<name>/` and reference it from
   `apps/kustomization.yaml`.
2. For SSO: add an OAuth2 or proxy provider + application + group binding to the
   Authentik blueprint (OIDC for native support, forward-auth otherwise).
3. Commit and push, then `just reconcile`.
